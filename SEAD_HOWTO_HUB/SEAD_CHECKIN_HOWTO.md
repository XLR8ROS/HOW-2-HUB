# SEAD CHECK-IN HOW-TO

## Timestamp
20260411 164903 EDT

## Purpose
This how-to defines how SEAD work should be checked in once work is active.

It exists to keep SEAD work visible without turning updates into filler.

It does not replace any agent-level heartbeat or office-level reporting contract.

## Core rule
A check-in should only happen when it adds useful execution clarity.

A check-in should not be filler.

## When to check in
Check in when one or more of the following is true:

1. work has started
2. a meaningful step has been completed
3. the current step has changed
4. a blocker appears
5. a blocker clears
6. timing has materially changed
7. a decision is needed
8. a due checkpoint is reached
9. the work is complete

## What a SEAD check-in should answer
A good SEAD check-in should answer:

1. what is being worked on
2. what just changed
3. what the current step is
4. whether anything is blocked
5. what happens next

## Good check-in shape
A check-in can be short.

Example shape:

1. current work
2. progress since last check-in
3. blocker, if any
4. next step

## Bad check-in shape
Avoid:

1. filler updates with no state change
2. repeated updates that say nothing new
3. vague phrases like “working on it” without current step
4. silence after a meaningful change or blocker

## Timing rule
If timing matters, state it.

If timing does not matter, do not force it.

## Completion rule
When work completes, the final check-in should say:

1. what was completed
2. what the result is
3. what the next step is, if any
