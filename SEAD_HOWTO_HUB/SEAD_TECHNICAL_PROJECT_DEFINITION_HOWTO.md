# SEAD TECHNICAL PROJECT DEFINITION HOW-TO

## Timestamp
20260411 164903 EDT

## Purpose
This how-to defines how SEAD should define a technical project before treating it as properly scoped.

## Core rule
A technical project is not properly defined until the objective, scope, dependencies, and done-state are explicit.

## What a technical project definition should answer
A good technical project definition should answer:

1. what is the objective
2. what is in scope
3. what is out of scope
4. what is already locked
5. what is still unsettled
6. what dependencies exist
7. what must be delivered
8. what the staffing pattern is
9. what the model-routing plan is, if relevant
10. what risks exist
11. what finished looks like

## Good project definition shape
Use this shape:

1. Objective
2. Scope in
3. Scope out
4. Locked decisions
5. Unsettled decisions
6. Dependencies
7. Deliverables
8. Staffing pattern
9. Model-routing plan
10. Risks
11. What finished looks like

## Done-state rule
The done-state must be concrete.

Good examples:

1. schema finalized
2. interface contract defined
3. routing policy documented
4. implementation validated
5. migration path recorded
6. tests passing
7. repo placement locked
8. review notes resolved or accepted
9. handoff package ready

Bad examples:

1. made progress
2. first pass done
3. mostly complete
4. ready for next phase without explicit criteria

## Adjustment rule
If the project changes materially, update the definition instead of pretending the original still fits.
